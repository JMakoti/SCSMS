**Right now, the desktop app’s login is only a demo gate—not real authentication.** The shared `login page` accepts a hard-coded email and password, then `stores the email in localStorage`. The dashboard trusts that value, but it doesn’t verify a user or check permissions. Although the SQLite schema already has users, password hashes, roles, and a `permissions_json` field in `user.ts`, I found no actual permission enforcement.

The most important security issue is the desktop `run_sql Tauri command`: it lets the webview submit arbitrary SQL. Hiding a button or protecting a route in React won’t stop someone from calling that command directly. Also, the `seed code` contains a default admin password, which should not be used in a production release.

**Recommended approach:**

1. **Move login verification into Rust.** Add a Tauri `login` command that checks the user’s status and verifies the password hash. Return only safe user details and permissions—not the hash.
2. **Keep the authenticated session on the Rust side.** Don’t treat `localStorage` or a user object supplied by the frontend as proof of identity. Clear the session on logout; persist it only if needed, using the OS credential store.
3. **Enforce authorization in the Rust commands that perform sensitive work.** Define permissions such as `schools.read`, `schools.update`, and `users.manage`. The UI can hide unavailable actions for usability, but Rust must make the actual allow/deny decision.
4. **Replace or constrain the generic SQL bridge.** Prefer specific commands for application actions. As long as the webview can execute arbitrary SQL, role checks elsewhere can be bypassed.
5. **Remove the fixed demo login and default password.** Use a first-run admin setup or another deliberate provisioning process; don’t silently create a known production credential.

If this desktop app must work **offline**, local authentication can control normal app use, but it cannot fully protect local data from someone who controls the computer or database file. If users need centrally managed accounts or stronger authorization, make a server the authority and have the desktop app authenticate and authorize through its API.
